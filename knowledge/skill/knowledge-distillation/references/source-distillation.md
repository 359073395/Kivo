# 资料蒸馏

开始前确认来源已经形成完整文字稿；视频、音频和 PDF 没有完整文字稿时先执行文字化流程。

## 1. 定义目的

让用户目的落入一种或多种：

- `what they do`：提炼方法、步骤、工具、适用条件和执行顺序；
- `how they think`：提炼作者关注的变量、因果模型、权衡方式、提问顺序和反例；
- `solve my problem`：只提取与当前问题有关的证据和行动方法，同时保留来源边界。

用户认真读过来源时，可结合其理解进行交互式校准；用户没读过或不熟时，直接做证据驱动的初版，但必须标注解释性推断，并提醒回到原文核对关键结论。

## 2. 建立覆盖表

按章节、页面、时间段或子页面列出处理范围。每一项标记 `complete`、`partial`、`blocked` 或 `not_applicable`。覆盖表未闭合时，不得标记完整蒸馏。

## 3. 拆解来源

分别提取：

- 有日期和出处的事实；
- 作者观点与假设；
- 方法、输入、步骤与工具；
- 思维框架、变量、因果和取舍；
- 适用/不适用条件；
- 例子、反例、失败模式与异常；
- 检查、成功信号和停止条件；
- 与知识库现有规则的重复、冲突和时效差异。

## 4. 编译为可调用单元

先形成方法卡或决策单元，再判断是否晋升为 Skill。一个合格执行单元应包含：触发情境、最低输入、硬门禁、执行步骤、判断标准、检查、停止/转人工、输出和反馈字段。

大型来源通常应拆成多个边界清晰的方法单元，再优先同步到已有主 Skill；只有现有职责无法承接时才考虑多个新 Skill，不能制造一个包含所有思想的万能 Skill。纯概念、背景事实或只适合阅读的内容留在 `资产/`，不强行做成 Skill。

## 5. 对照原文与现有库

- 为关键主张保留页码、时间戳或子页链接。
- 抽查原文，确认没有把例子误写成通用规则。
- 优先更新最窄的权威页面，避免近义重复。
- 新来源与明确的用户当前规则冲突时，按高优先级规则裁决并记录，不静默覆盖。
- 冲突会改变总结或 Skill 执行、且当前权威无法裁决时，先把冲突双方、来源、影响和选项列给用户；答复前标为 `conflict_pending_user`，不完成该冲突部分的最终总结。

## 6. 同步现有 Skill 或生成候选 Skill

先为每个方法指定现有主 Skill 和模式。用户确认或验证通过、无未决冲突的方法，同步到现有 Skill 的路由、RUNBOOK 或 reference；报告其自动触发和停止条件。

只有现有 Skill 无法承接时才生成候选 Skill：写出准确的 `name` 与 `description`，说明能力、触发语句和相近任务边界。正文只保留核心流程与不变量；模式细节、长表格、脚本和模板分开放置。使用 `skill-creator` 校验结构。来源知识默认仍是候选；至少准备一个真实任务或回测方案，通过后再注册为活动入口。
