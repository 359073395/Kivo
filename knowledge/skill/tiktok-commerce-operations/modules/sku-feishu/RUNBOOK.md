# 内部执行手册：SKU、定价、Flash Deal 与飞书派工

> 本文件不是独立 Skill。只有 `tiktok-commerce-operations` 路由到 `pricing_campaign` 或 `sku_dispatch` 时才读取。旧 `tiktok-sku-feishu-management` Skill 已归档。

## 路径与事实源

1. 从 `辅助/配置/machine-paths.local.json` 读取 `tiktokSkuRoot` 与 `zhanfuBrowserRoot`。
2. 路径为空、目录不存在或来源角色不清时，不得回退到 `G:`、`F:`、Skill 目录或旧项目目录。
3. 店铺产品表、价格源、活动模板、生成文件和在线表运行数据都属于外部本地工作目录；知识库只保存规则、摘要和复盘。
4. 只使用本次确认的当前主价格表、店铺导出和飞书链接。历史个人表 token、旧折扣/佣金常数和旧“猫店 + 数值”规则不自动生效。
5. 仓库SKU与价格源读取主Skill的 `references/current-warehouse-source.json`，先运行 `scripts/validate_current_warehouse_source.py --mode source-read`，相对 `tiktokSkuRoot` 解析文件并验证SHA-256；当前为10.12版，7.21版仅历史对照。读取其知识资产了解缺价、作废、库存待查和重复SKU，不将状态文字当作自动执行授权。仅更新知识源的任务不运行Flash写入。

## 共同门禁

- SKU 是仓库/定价键；线上活动上传必须使用该店当前产品表中的 `Product_id`。
- 精确匹配 `store + SKU`，禁止跨店复用 product ID、模板或 Listing 事实。
- `unknown`、空白、冲突不等于 0。
- 清仓/下架、同 product ID 多SKU最终价不同、缺价或身份冲突停止受影响 product ID。Npcs 不再一律排除，按下述统一定价规则处理。
- 佣金、折扣、净额、四舍五入和价格有效期必须来自本次输入或已登记的活动规则；缺少时可做带假设的分析，但不能写线上或上传文件。

## Flash Deal 当前流程

1. 每店从当前活动页面取得该店原始 `Flash Deal.xlsx`，并验证店铺、活动和模板新鲜度。
2. 在内存中完成整批 SKU、product ID、价格资格和冲突检查；先列出阻断项，再执行写入。
2.1 价格差异门禁：公式/源版本改变时，先比较旧Flash价、新价、两项源价和新旧仓库源，展示涨跌数量、最大金额和最大比例；大幅差异或字段/单位异常必须主动提醒，保留受影响项待用户决定。价格计算正确不能代替源价合理性检查，不自行设定永久阈值。
3. 默认直接填写每店原始 `Flash Deal.xlsx`，不生成 `Flash Deal_已填写.xlsx`、备份副本或单独审计工作簿。
4. 只补丁授权单元格，保持原 OOXML ZIP 条目、关系、样式、验证、表名和元数据；不得用会重写工作簿包结构的方式保存官方模板。
5. 使用临时文件完成写入和校验后原子替换原路径；重新打开并核对 exact `Product_id`、`Deal Price`、ZIP 条目和工作簿可读性。
6. 只有用户明确要求时才把输出改为副本或另建审计表。
7. 默认不参加大促；只有用户对本次活动明确告知“参加大促”时，才切换到另行确认的大促口径。不得从文件名、旧表或历史活动推断参加大促。
8. 普通定价先生成并校验 `tiktokSkuRoot/04_输出结果/SKU统一定价表_价格1与价格2取低.xlsx`：价格1=当前源指针登记的仓库表E列猫店参考价先加8000，再乘1.05（整数IDR向上取整）；价格2=`Y仓 TK SHOP SKU 售价_活动价.xlsx`平台活动价；最终价格=`min(价格1, 价格2)`。E列已含源表“普店+3000”，不得另加一次3000。
8.1 统一价格表的源哈希必须对应当前源；执行Flash前运行 `scripts/validate_current_warehouse_source.py --mode flash-write`，只有返回 `allowed=true` 才可进入写入。若源已更新、指针标记需要重建或缺少一致的源版本证据，脚本必须返回 `stop_stale_unified_price_rebuild_required`，先重建并通过价格与精确SKU门禁，不能直接写Flash。重建完成后登记实际源哈希、派生表哈希、生成时间与验证结果，再把当前源指针中的派生状态改为 `current_for_source`。2026-09-12入库时，9月2日统一价格表尚未重建，9月9日Flash尚未重定价。
9. 2026-10-10用户明确：Npcs最终价=基础SKU最终单件价×N。先对基础SKU精确匹配并完成当前单件定价，再乘正整数数量；不得优先使用独立组合报价，不重复加8000或5%。单件价格缺失/冲突时停止受影响项。展示售价与活动价分别使用同口径单件价，不能互相替代。Flash多SKU商品跳过规则仍有效。
10. 仅允许使用用户已逐项确认并登记的一对一 SKU 别名。Y仓别名读取 `references/confirmed-y-sku-aliases.json`：`HK FOOT PASTE` → `HK FOOT PASTE 足贴`；仓库价格1别名读取 `references/confirmed-warehouse-sku-aliases.json`：`Face LIFT01= Pink FAY` → `Face LIFT01=Pink FAY`、`NUGEN BIoom` → `NUGEN Bloom`（2026-09-14用户确认）。先精确匹配原SKU，再查询该源明确别名；Npcs基础SKU拆算也只可使用已确认基础别名。除此之外仍严格精确匹配，禁止模糊匹配、相似品名匹配、普遍去空格或I/l替换。
10.1 只允许 `references/confirmed-price-overrides.json` 中用户确认的精确SKU例外绕过双价格门禁。当前确认：`626-Expce Herbal Tea` 的价格1为空时，使用价格2 `59,520 IDR`；不得推广到其他SKU。
10.2 仓库别名执行复用 `scripts/warehouse_sku_aliases.py`，运行 `scripts/test_warehouse_sku_aliases.py` 验证两项别名、原精确SKU优先、目标缺失不补价及禁止泛化替换。
11. 同一SKU可对应同店多个Product ID，也可对应不同店铺的不同Product ID；Product ID必须店铺独立，跨店重复视为异常。2026-09-22用户明确确认：同一Product ID对应多个不同SKU时，整项跳过，不论价格是否一致，不再为此重复询问。按精确SKU去重计数，单个Npcs SKU仍可参与。单SKU商品若必要源价缺失、非数值、冲突，则停止该Product ID并询问用户，不猜价、不静默少填。已由用户确认不填写的精确店铺+Product ID必须登记在 `references/confirmed-flash-product-exclusions.json`，脚本只能放行这些精确阻断项。
12. 后续Flash Deal只从已校验的统一SKU价格表读取最终价格，旧版本B、旧Flash价格和旧安全线回退不再参与未来定价。脚本运行时必须显式传入 `UNIFIED_PRICE_WORKBOOK`；默认只预检，存在价格阻断时禁止 `APPLY=1`。
13. 当合格商品数超过官方模板预留行时，新增行只能复制写入前保存的纯净空白样式行，并在写值前移除样式行中的 A/B 单元格；严禁复制已经填入首个商品的行。原子替换前必须直接检查 OOXML：每个有数据的行只能有一个 A 引用和一个 B 引用，不得存在重复单元格引用；Product ID 必须唯一；C/D 等未授权列不得出现值；有数据行数必须等于合格商品数。任一项失败，保留原文件并停止该店。

运行 `scripts/sync_weekly_flash_deals.py` 时必须显式传入 `UNIFIED_PRICE_WORKBOOK`，指向当前已校验的统一价格表。该脚本不再读取旧版本B、旧Flash价格、安全线或宽松Y仓回退。结构校验必须直接读取 OOXML，不能只依赖 Excel/OpenPyXL 的值回读，因为重复 A/B 引用可能被值读取器静默折叠。

`scripts/generate_flash_deal_uploads.py` 保留为历史审计脚本，尚含旧版本B/安全线/Npcs排除逻辑；在迁移到 `COM-012` 前禁止用于新的Flash Deal任务。新任务只允许使用读取 `UNIFIED_PRICE_WORKBOOK` 的 `scripts/sync_weekly_flash_deals.py`。

## 飞书派工

1. 先读取用户本次给出的飞书表或项目摘要，校验表格 token 和表结构。
2. 保持 `待处理派工`、`SKU状态总控`、`员工执行清单` 和店铺视图的职责分离。
3. `预购/开预购`、`关预购/到货`、`下架`、`恢复正常` 只有语义明确时才规范化；不明确标记 `待确认`。
4. 任何在线写入先做小范围读写验证，写后回读；不因旧对话里存在链接就默认使用。
5. 常用确定性脚本位于 `scripts/`，运行时所有输出必须显式指向外部任务目录。
6. 当前十店原飞书表采用 2026-10-10 用户要求的新闭环，先恢复 `项目/进行中/20261010_十店SKU总览与飞书任务闭环.md`。任务输入保留在固定行，逐店完成和整项完成均可用，待办自动清理、完成记录保留；旧 SKU 状态/执行表已保留为历史，不重新激活旧多店公式。每次已授权在线产品更新后同步当前商品事实、SKU索引和店铺视图；不得覆盖用户未完成任务、完成状态或备注。事实刷新前核查未完成任务目标集合是否改变。

## 停止条件

店铺、SKU、product ID、价格口径、模板、飞书权限或写入范围不清时，停止对应单元。不得为了完成批次采用旧默认常数、旧路径、跨店模板或 AI 推算。

## 每次上架更新的必做收尾（COM-016，2026-10-10）

用户明确要求“以后每次更新店铺上架产品的时候都要同步一下”。对当前十店，每次实际完成已授权上架、在线商品更新或产品表刷新，都继续同步原飞书总览，不限周更、不需重复提醒。先恢复 `项目/进行中/20261010_十店SKU总览与飞书任务闭环.md`；以更新后核验的来源刷新商品、各店明细、SKU 索引/查询、派工价格参考和 Npcs 核对，标明各店真实数据日期。保留原任务、备注与完成状态，未完成任务目标变化先列差异，不把旧完成套给新链接。

**完成门槛：店铺更新＋飞书同步回读核验均通过。** 飞书失败时保留待补同步记录，报告未同步店铺及旧日期，不称整项完成。只写本地文案草稿不算实际上架；不因此建立后台定时监控或扩大线上操作授权。来源：`资源/来源索引/2026-10-10_上架产品更新必须同步飞书.md`（相对知识库根）。
